# Devices API

A REST API for persisting and managing device resources: create, update (full or partial),
fetch (one, all, by brand, by state), and delete, with business rules enforced around a
device's state.

## Prerequisites

- **Docker** (with Docker Compose) — the only requirement to run the application.
- **JDK 21+** — only needed to build or run the test suite outside Docker. The Maven
  Wrapper (`./mvnw`) is included, so a local Maven installation is not required.

## Quick start

```bash
docker compose up --build
```

That starts PostgreSQL and the API together. Once the app reports healthy:

| | |
|---|---|
| API | `http://localhost:8080/api/v1/devices` |
| Interactive API docs | `http://localhost:8080/swagger-ui.html` |
| Health | `http://localhost:8080/actuator/health` |
| Metrics | `http://localhost:8080/actuator/prometheus` |

Stop everything, including the database volume, with `docker compose down -v`.

## Try it

```bash
# Create a device
curl -i -X POST http://localhost:8080/api/v1/devices \
  -H 'Content-Type: application/json' \
  -d '{"name":"Pixel 9","brand":"Google","state":"AVAILABLE"}'

# List devices (paginated, newest first); add ?brand=Google and/or ?state=AVAILABLE to filter
curl http://localhost:8080/api/v1/devices

# Fetch one (use the id returned by the create call)
curl http://localhost:8080/api/v1/devices/{id}

# Partially update - omitted fields are left as they are
curl -X PATCH http://localhost:8080/api/v1/devices/{id} \
  -H 'Content-Type: application/json' \
  -d '{"state":"IN_USE"}'

# Renaming a device that is in use is refused (409)
curl -i -X PATCH http://localhost:8080/api/v1/devices/{id} \
  -H 'Content-Type: application/json' \
  -d '{"name":"New Name"}'

# Deleting a device that is in use is also refused (409)
curl -i -X DELETE http://localhost:8080/api/v1/devices/{id}
```

## Domain model

**Device**
- `id` — UUID, generated by the application.
- `name` — required.
- `brand` — required.
- `state` — one of `AVAILABLE`, `IN_USE`, `INACTIVE`.
- `creationTime` — set once when the device is created, never by the client.

**Business rules**
1. `creationTime` cannot be changed after creation.
2. `name` and `brand` cannot be changed while the device is `IN_USE`.
3. A device cannot be deleted while it is `IN_USE`.

## API

```
POST   /api/v1/devices                → create
GET    /api/v1/devices/{id}           → fetch one
GET    /api/v1/devices?brand=&state=  → fetch all / filter by brand / filter by state
PUT    /api/v1/devices/{id}           → full replacement (every field required)
PATCH  /api/v1/devices/{id}           → partial update (omitted fields left unchanged)
DELETE /api/v1/devices/{id}           → delete
```

Brand and state are query parameters on the collection rather than separate routes, so the
two filters can be combined. The collection is paginated (`page`, `size`, `sort`; 20 per
page, newest first by default).

Errors use a consistent, standard JSON shape with a `status`, a short `title`, and a
human-readable `detail` — for example:

```json
{
  "title": "Device In Use",
  "status": 409,
  "detail": "Device is in use and cannot be deleted: 3f1c...",
  "instance": "/api/v1/devices/3f1c..."
}
```

## Assumptions

These weren't specified in the requirements, so they were decided one way and are called
out here rather than left for a client to discover:

- **The brand filter matches exactly and is case-sensitive.** `?brand=Google` will not
  match a device stored as `google`.
- **Names and brands are stored exactly as sent** — leading and trailing whitespace is not
  trimmed, so `"Pixel 9 "` and `"Pixel 9"` are different values. Entirely blank values are
  rejected.
- **Any state transition is allowed.** The rules restrict what can change *while* a device
  is in use; they don't restrict which state it can move to.
- **Re-sending a device's current name or brand while it is in use is allowed**, since
  nothing actually changes. Only a real change is refused.

## Tech stack

| Concern | Choice |
|---|---|
| Language/runtime | Java 21, Spring Boot 3.5 |
| Build tool | Maven (wrapper included) |
| Database | PostgreSQL, schema managed by Flyway migrations |
| Architecture | Layered (controller → service → repository), business rules on the entity |
| API docs | springdoc-openapi (Swagger UI) |
| Concurrency | Optimistic locking |
| Tests | JUnit 5, Mockito, Testcontainers (real PostgreSQL, never in-memory) |
| Containerization | Multi-stage Dockerfile + Docker Compose |
| Coverage | JaCoCo report |

Design decisions and their trade-offs are documented in
[`docs/DECISIONS.md`](docs/DECISIONS.md).

## Testing

```bash
./mvnw verify
```

Requires Docker to be running, since the repository and integration tests start a real
PostgreSQL container. 60 tests across four levels:

1. **Domain unit tests** — the business rules, with no framework involved.
2. **Service unit tests** — orchestration, with the repository mocked.
3. **Repository tests** — real PostgreSQL, covering the migrations, queries, and
   concurrent-update handling.
4. **Integration tests** — the whole application over real HTTP.

A coverage report is written to `target/site/jacoco/index.html` (currently 98% of
instructions, 90% of branches).

## Known limitations / future improvements

- **No request correlation ID.** Useful for tracing a request across services; of limited
  value for a single service of this size, so it was left out rather than added
  speculatively.
- **Clients can't detect a conflict before writing.** The server prevents two concurrent
  updates from overwriting each other and returns `409` to the loser, but it doesn't
  support the HTTP headers (`ETag`/`If-Match`) that would let a client check first.
- **Coverage isn't enforced.** The report is generated on every build, but nothing fails
  the build if coverage drops — see `docs/DECISIONS.md` #15.
- **Sorting isn't restricted to an allow-list.** An unknown sort field is rejected with a
  `400`, but any real field is sortable; there's no curated list of which ones are
  intended to be part of the public contract.
- **No bulk or search endpoints.** Filtering is exact-match on brand and state only; there
  is no partial-text search.
